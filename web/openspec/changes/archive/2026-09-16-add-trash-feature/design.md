## Context

删除需要在"可恢复"与"立即释放"之间取舍，并保持与既有的文件/DB 结构兼容。
回收站以 `"delete"` 标志位实现，文件移入数据目录下的 `.delete/`。

## Goals / Non-Goals

**Goals:**
- 应用内可查看/恢复已删除的节点
- 三种删除模式语义清晰、互不冲突
- 保留期可配置，并在启动时清理
- 已删除节点不出现在任何查询中

**Non-Goals:**
- 不联动处理附件图片（`attachment/img/` 保持不变）
- 不改变附件目录结构

## Decisions

- **保留期复用 `last_up_time` 单列双用**（最近修改 / 删除时间），不新增 `deleted_at`：
  删除后节点在回收站内不可编辑，且除回收站外无其他入口，故两个语义不会冲突
- **回收站按「删除簇顶层」展示**：`"delete"=1` 且父节点非 `"delete"=1`；
  恢复 = 顶层节点 + 其所有 `"delete"=1` 后代。这样天然区分"整树删除"与"单节点删除"（后者子节点已上移且未删），
  **无需额外标记列**
- **根节点永不删除、永不进回收站**：删根 = 递归删除其所有子孙，根保留为空根。
  因为 MindMap 在无根时会用硬编码 id `'1'` 自动建根，软删根会撞主键；改用新 id 又会产生第二个 `top='0'` 的根
- **`delete` 是 SQLite 关键字**：所有 SQL 必须写 `"delete"`（带双引号）
- **查询过滤放在共享的 `Table` 层**：默认追加 `"delete" = 0`，并提供 `includeDeleted` 例外
