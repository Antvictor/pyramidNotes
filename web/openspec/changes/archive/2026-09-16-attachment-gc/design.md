## Context

图片只增不删。清理的难点不在"删文件"，而在**判断某张图还有没有人用** —— 而这不能用文件名推断。

## Goals / Non-Goals

**Goals:**
- 删除笔记后释放它**独占**的图片
- 编辑器里删掉的图，无人引用后也被释放
- 回收站中的笔记（可恢复）**不丢图**
- 清理成本可忽略

**Non-Goals:**
- **不做内容去重**（保持"每次粘贴新建"）：去重会让图片跨笔记共享，机制更复杂，
  而它省下的扫描时间本就微不足道（0.025 ms）
- **不改命名**（引入 id 前缀）：文件名已全局唯一，无需改
- 不联动处理附件目录之外的资源

## Decisions

- **归属只按「引用」判断**：扫 `notes.content` 里的 `![[文件名.ext]]`。
  文件名全局唯一 ⇒ 引用无歧义；**绝不按文件名前缀**推断（同名笔记 + 重命名会让前缀失真）。
- **扫描包含 `delete=1`**：回收站里的笔记仍占住它的图片，恢复后不会缺图。
- **按图片扩展名过滤**：`![[...]]` 与节点嵌入共用语法，不过滤会把节点嵌入收进引用集合。
- **清理时机 = 启动 + 永久删除后**，**不**在保存时：
  保存时删会让"删图后撤销"丢图；启动时删则天然给了撤销余地，且顺带清理历史孤儿。
- **清理函数自身 try/catch**：扫除失败不得影响启动或删除主流程。
- **取目录用 `resolveStoragePath()` 拼路径**，不用会 `mkdir` 的 `resolveAttachmentDir()`
  （否则没用过图片的用户每次启动都会多出一个空目录）。
- **假设**：DB 的 `notes.content` 是引用真源（`saveFile` 同时写 `.md` 与 DB）；
  若在应用外手改 `.md`，DB 可能滞后 —— 已记入 `ATTACHMENT_DESIGN.md`。
